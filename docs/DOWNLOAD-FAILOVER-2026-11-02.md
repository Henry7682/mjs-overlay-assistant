# GitHub 慢速下载与国内切换修复

状态：1.0.5 后源码修复，未发布；当前发行文件、签名清单和用户配置不变。

## 发现的原因

1. 旧下载器有单次读取 15 秒和总计 180 秒限制，但持续有少量进度时不会提前换源。发行验证中的一次匿名 GitHub 下载用尽 180 秒，留下约 119 MB 断点，第二次才完成；这是实际网络记录，不是 Gitee 已完成切换的证据。
2. 完整包地址全部重试两遍后才尝试分卷。Gitee 通常使用分卷，轮到它时可能已经没有总时间。
3. 本轮匿名读取 GitHub/Gitee main，均为 1.0.5、`mirror_verified=false`，没有该版 Gitee payload 地址。客户端不能凭空推断附件地址，也不能拿旧版镜像冒充当前版。
4. 固定外层启动器的下载组件没有随程序更新。仅新 payload 内包含修复，不能让旧外层自动采用它。

## 新行为

- `Auto` 先尝试清单里的完整包源；存在其他有效路径时，观察至少 8 秒，平均速度低于 256 KiB/s 且剩余超过 1 MiB，提前换源。正在阻塞的读取仍受 15 秒读取超时约束，不承诺正好第 8 秒切换。
- 每个源先尝试一遍，包括完整可下载的 Gitee 分卷，再重试；有后续路径时，本次最多使用 45 秒、且最多占剩余总预算的一半。最终源可使用剩余时间。
- 只有一个可用源时不因低速主动放弃。全部失败仍启动原版本；启动器总下载预算保持 180 秒，下载器保留自身 15 分钟预算。
- 每个 URL 独立保存断点，旧版单文件断点在 URL/哈希一致时迁入。只在服务端 Range/ETag 一致时续传，否则完整重下；分卷和最终包继续验证大小与 SHA256。`S` 取消不触发后续换源。
- 元数据总检查预算仍约 8 秒，为两端分配时间。签名都有效、版本相同、对应资产名称/大小/哈希相同时可合并两端下载地址；不会从较旧镜像借包或混入不一致文件。
- 下载器显式 `-Source GitHub`/`Gitee` 仍限制来源；慢速切换的正常使用方式是默认 `Auto`。

## 后续版本如何持续获得修复

新版下载库带有兼容标记，外层库按 `current.json` 委托给已安装的当前版本库；仍使用旧协议，不提高 `minimum_launcher`。

对于已安装 1.0.0–1.0.5 外层启动器的用户，新版冻结程序会在 OCR 模型初始化、启动握手以及 `current.json` 提交完成后，原子替换外层 `release/Release.ps1`，保留 `.previous` 备份。只替换兼容下载组件，不替换公钥、入口脚本或用户数据；失败会记录并继续运行。源码模式不执行迁移，更新回滚前不替换。

因此旧启动器**首次下载包含修复的新版本时仍使用旧逻辑**。首次升级成功后的后续启动才获得自动低速切换。无法完成这第一次下载的用户需用新下载器或新完整便携包进行一次引导；不能通过更改服务器清单远程修改其旧脚本。本轮没有发布包含修复的安装包。

## 发布门禁

`tools/check_update_channel.py` 的命令行默认要求 `mirror_verified=true` 和五种国内资产的完整路径。`--allow-github-only` 仅用于检查尚未完成的候选通道，不表示国内验收完成。

每次发布仍需：上传同版本附件 → `verify_mirror.py` 匿名下载全部分卷并校验 → 对最终清单签名 → 同步两个 main → 实测断网/慢速切换。Gitee 只是导入源码或上传旧附件都不满足要求。签名清单可在不改包内容的情况下补充镜像地址；不覆盖已发行附件。

## 验证与限制

- Windows PowerShell 5.1 使用可控流测试实际读取循环：每 2.1 秒仅返回 1 KiB，8 秒后记录 `slow`，切换备用源并验证成品哈希，原源断点保留。
- 测试分卷先于 GitHub 重试、无备用源时继续、指定来源、取消、错误包拒绝、旧断点续传和服务器忽略 Range、同版地址合并/异版与错误签名隔离。
- 测试提交后的下载库迁移、提交前/回滚期间不迁移、旧库与错误库保留外层、只读目录失败保留可用脚本，原配置保持。既有启动握手和失败回滚集成测试继续运行。
- 上述模拟的是网络速度和服务器反馈，未将其称为真实 Gitee 冷下载验收。实际在线 1.0.5 镜像地址缺失；新版冻结包、旧版到新版的真实下载升级、国内网络和 Win10 实机仍需发布前验证。
