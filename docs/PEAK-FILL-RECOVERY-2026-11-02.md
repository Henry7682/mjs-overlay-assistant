# 巅峰填名中途返回：日志诊断与修复

基线为合入PR #18后的d4f1c04（包含3777023），运行身份为1.0.4-dev。本文补充并修正[整链路提速记录](QUERY-LATENCY-2026-11-02.md)，不覆盖此前组件对照数据。

## 已确认原因

1. **30秒目标提前截断输入。** 原代码从首次识别选将开始计算30秒目标，再减去返回与读取余量作为输入截止点。实际请求中，02:13输入12/14名后停止，02:24输入13/14名后停止，02:55输入12/14名后停止；日志明确为“优先返回已读攻略，候选输入未完成”。这些不是窗口激活失败，也不是已确认的游戏阶段取消。单一14人名单组件测试没有暴露其他名单和整链路启动耗时带来的回归。
2. **攻略文字被误判为数量限制。** 02:41请求输入第8名蒙恬后，第一份回读仍为7名。全页文本正则把已读攻略中的“上限养大哥。个”匹配成数量上限，立即停止剩余7人。随后名单迟到更新，触发“读取期间小程序候选发生变化”。诊断事件中的攻略理由与原正则可以直接复现误匹配。不是蒙恬不存在，也不是证实小程序仅允许7人。

上述两条可以解释本次日志中的具体中断，不代表所有历史UIA慢调用或退出都已解决。02:12另有石崇头像不可点击与重试耗时；未知头像仍按局部失败处理，不能虚构为成功选入。

## 修复边界

- 30秒仍是尽快返回的目标，仅限制额外结果滚动；填名使用40秒硬预算内的可用时间，并从硬截止预留4秒处理结果。正常输入不在约22～24秒被软目标截断；不承诺全部查询都能在30秒内完成。
- 不从包含攻略的全页文字推断候选数量上限。迟到的已选标签继续按现有短时核验与最多一次重试处理；单名未选入记录缺项后继续其他姓名。若真的遇到数量限制，本次会按未确认姓名报告，不伪称已识别明确数量上限。
- 保留逐名确认、重试前检查避免重复切换、阶段性攻略回传、错误名单与取消处理、40秒父进程硬截止。普通楚汉15秒预算不变。
- 没有增加成功路径的UIA调用或固定等待，没有更改OCR、模式/阶段识别、禁将筛选、浮窗或游戏操作。输入较慢的请求可以比原先的部分返回更久，但用于继续提交候选，不是增加操作间隔。
