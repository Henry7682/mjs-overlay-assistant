# 维护与升级入口

1. 阅读 AGENTS、TODO、TESTING；私人工作区存在 WORKSPACE 时按它找到唯一公开 checkout。旧根历史、实验和发行目录不能替代当前源码。
2. 源码准备、独立数据、启动见 [DEVELOPMENT](DEVELOPMENT.md)。普通用户入口仍为便携版外层 launch.cmd。
3. 分支、提交、PR、保护、合并与四种交付状态见 [GIT-WORKFLOW](GIT-WORKFLOW.md)。遵守 main 规则，不设临时绕过。
4. 构建、签名、不可变资产及双渠道验收见 [RELEASING](RELEASING.md)。源码更新不等于已发布，主线签名清单不能提前指向未验收资产。
5. 每次记录单元/回放/组件/实战的独立证据，维护 TODO，不覆盖历史失败结论。未经 Win10 实机验证的项目持续标明。
6. 只清理经核对可重建缓存或具有完整保留副本的中间产物，留下路径/哈希/保留位置清单；不清理唯一素材、用户配置、已发布资产或私钥。目录迁移先核对绝对路径、占用、Git和内容，迁移后复验。

本轮开发身份与目录整理不新增发行、不更新实际用户配置、不操作游戏或小程序。历史未发布实验按独立任务逐项评审，不能整库覆盖主线。


## 本地工作区管理（每轮任务及发布前执行）

- 开始先读工作区导航，确认唯一公开 checkout、当前分支/提交、实际启动入口和数据目录；业务代码只在该 checkout 修改。私人根、录制分支和旧发行包不得当作默认源码。
- 每次新增大文件/构建前检查目标盘剩余空间。源码、独立环境、构建和测试数据放在维护者指定盘；空间不足先盘点可清理项，不静默改用其他盘。临时目录、PyInstaller 缓存也显式定位，保留唯一一套当前开发环境。
- 盘点按目录给出文件数和逻辑大小，跳过目录链接避免重复统计；磁盘实际释放量单独测量，硬链接、压缩和回收站可能使两者不同。
- 当前维护策略：本地不保留 1.0.0 之前的可运行分发版本。旧源码历史、发行说明、测试结论及独有配置/日志/素材继续保留；先从旧目录保存并校验这些数据，再清理程序与依赖。不得借清理 Git 历史丢弃实验或未提交修改。
- 1.0.0及以后正式资产、标签与签名清单保留；相同文件的重复下载和已验证的 staging 可清理，先核对完整保留副本/ZIP内容和SHA256。失败候选、唯一实战画面及诊断包不能当缓存删；无法复核时保留并列待办。
- 清理前核对绝对路径在目标工作区内、不是链接、无运行占用、无追踪源码或唯一证据。只处理清单内目标；记录原路径、原因、大小、哈希、保留副本或迁移位置。优先移入回收站，完成后提醒维护者检查并清空；不擅自清空整机回收站。
- 不自动清理用户data、签名私钥、无关项目、宣传原片。依赖缓存只留校验过的一套，重复安装测试虚拟环境可重建，保留安装报告/锁文件。
- 结束更新 WORKSPACE/TODO/TESTING，写清清理范围、实际剩余空间、被移除的旧证据入口及替代位置。不要把本地清理当作 GitHub Release 删除，也不要把无原始证据当作测试通过。
